## Architecture and lifecycle

The Manager saves each original user message and run as Week 3 history events. `SessionMemory` selects complete historical run groups using a local 2,000-token short-term target. It first persists uncovered overflow in a buffer. `MemoryProcessor` summarizes the buffer in ordered chunks and extracts facts from original user messages. A successful revision-checked save stores summary, facts, and covered run IDs together; failed processing retains the buffer and original history. Current-message extraction has its own processed-message marker; buffered runs identify previously extracted user messages. `ContextBuilder` supplies an honesty policy, the generated summary, facts, uncovered buffer, recent dialogue, and current message to the existing Manager. The policy instructs the Manager to acknowledge missing information, identify uncertainty and conflicts, respect corrections and distinguish requested actions from confirmed external results. Tool calls/results and request meters remain in history events. The original transcript is authoritative; summaries are not.

Week 3 uses `week3_sessions`, `week3_history_events`, and `week3_session_memory` in `d11/data/sessions.sqlite`. Memory contains `revision`, `covered`, `short`, `buffer`, `summary`, `facts`, and `extracted`. Confirmed/assumed facts include source IDs; corrections may retain prior values in `supersedes`. Legacy records without status are treated as assumed when merged or read through the facade. A deletion removes Week 3 memory and events with the session. Week 2 uses separate tables.

3. Open **Labs → Week 3**, create a uniquely named synthetic session, and inspect **Session stats → Session memory**. The UI shows short-term token estimate and messages, summary, and facts. Use the session menu to delete only the named test session after obtaining approval to clean it up.

Alternatively, with the backend stopped, use `sqlite3 data/sessions.sqlite 'SELECT id,title FROM week3_sessions;'`; query only the test session. Do not open credential stores.
5. Run `pnpm test`, `pnpm typecheck`, `pnpm build`, and `node --test server/session-integration.mjs server/sliding-integration.mjs server/week3-integration.mjs`. ## Seven reproducible conversations

**1 — Facts and corrections.** In order send: (1) `For project Cedar, my deadline is November 25.` (2) `I think the Cedar budget might be 48 units.` (3) `I prefer a blue cover for Cedar.` (4) `Actually, the Cedar deadline has changed to November 28.` (5) `Another schedule says Cedar is due November 30.` (6) repeat message 1. Before correction the expected deadline is confirmed November 25, budget assumed 48 units, and preference blue. After correction expect November 28 plus a trace of November 25. The November 30 statement should remain traceable as a contradiction, not erase the correction. Repetition must not create duplicate matching facts. Inspect stored status and sources, not just the answer. The model may phrase subjects differently; record any failure to merge semantically equivalent keys.

**2 — Memory overflow.** Send `Project Cedar decision: ship the blue cover on November 28. The unresolved task is to approve 48 units.` Then send 20 separate numbered messages for `i = 01` through `20`, each exactly `Block i: ` followed by `Synthetic packing item alpha beta gamma delta. ` repeated 40 times. Send each as a separate chat turn and wait for its reply. The short-term estimate should eventually exceed its 2,000-token target, move oldest complete runs to the buffer and produce a summary; covered IDs advance only after save. Verify the original first message and every block remain in events. Then send one message containing `oversized synthetic text ` repeated 3,000 times: expect a clear short-term budget error and no silent truncation of the saved original.

**3 — Repeated compression.** Begin `Decision: Cedar ships on November 28 with 48 units; Iris approves the artwork. Open task: confirm the carrier.` Send Scenario 2 blocks 01–20, then send `Update: the carrier remains unconfirmed; Iris still approves the artwork.` Send blocks 21–40 using the identical template. After each batch record `summary`, `covered`, and `facts`. Expect more than one successful coverage advance, no repeated IDs, and preservation of the original decision and open task. Ask `What date, quantity, and open task did we agree?` Compare the reply and saved memory to the initial statement, and inspect the complete event transcript.

**4 — Controlled context overflow.** Run `pnpm exec vitest run src/session-memory.test.ts -t 'recovers from a provider context overflow|stops after two smaller overflow retries|does not retry a rate limit'`. The synthetic inputs are an older repeated `older ` message followed by `question`; the mock returns a structured 400 context-overflow response, then `done`, or repeatedly returns overflow. Expect a smaller request before a retry, at most three answer calls total, and no retry for 429 or incomplete output. Run `-t 'recompresses a summary|retains the prior summary'` for summary-only recovery and persistence failure. This is mocked API-level evidence, not a browser/provider test.

**5 — Persistence and isolation.** Create sessions `QA Cedar A` and `QA Cedar B`. In A send `The Cedar meeting is at 12:00.` In B send `The Cedar meeting is at 15:00.` In each ask `What time is the Cedar meeting?` Inspect both memory endpoints and record IDs. Stop and restart only the dedicated backend, reload, and reopen both sessions. Expect A=12:00 and B=15:00 with separate histories and facts. Delete only A; its API returns 404, B remains unchanged, and an existing synthetic Week 2 control remains intact.

**6 — Honesty and fact history.** In a fresh session send, in order: `My appointment is on Tuesday.`; `I think the meeting might be at 10:00.`; `Actually, change my appointment to Monday.`; `My appointment is on Monday.`; `When is my appointment now, and what was the previous day?`; `What is the meeting time?`; `What is my passport number?`. Expected memory: appointment Monday as current, Tuesday under `supersedes` with its original source; the repeated Monday statement adds no duplicate; meeting time 10:00 remains assumed. The answer should state current and previous days, qualify the meeting time, and say the passport number is unavailable. It must not claim that an external booking was changed without an authoritative tool result. Reload and inspect the same facts and sources. Record false answers separately from storage errors.

**7 — Subject ambiguity.** In one new session send (1) `Alex's deadline is November 25. Mark's deadline is November 28.` (2) `What is Mark's deadline?` Expect November 28 and two separate facts. Send (3) `Alex discussed the project with Mark. He decided to postpone the deadline.` Expect a question such as `Who decided to postpone the deadline, Alex or Mark?` and no confirmed assignment. Send (4) `Mark. His deadline is now November 30.` Expect Mark November 30 with November 28 in `supersedes`, while Alex remains November 25. Inspect the memory API, restart the backend, reload and inspect again. Repeat steps 1 and 3 in at least three fresh sessions to measure provider consistency. Do not treat the mocked test as a live-provider result.

Developer check for scenario 7: **PASS (mocked)** for separate extraction associations, rejection of a swapped association and a guessed pronoun in three repetitions, captured Manager prompt and mocked responses, and SQLite correction restoration after restart. **BLOCKED / NOT VERIFIED (browser and live provider):** the browser access host was unavailable. ## Acceptance and known risks

P0: no loss of original history, cross-session contamination, unsupported facts presented as confirmed, ignored known corrections, silent confirmed-fact deletion or assumption promotion, duplicate committed processing, infinite retries, corrupt persistence, incomplete summaries accepted, or Manager/tool regression. P1: honest uncertainty, traceable corrections, historical values, correct summary updates, bounded recovery, restoration and memory UI. P2: minor visuals, nonblocking performance, existing build chunk-size warnings. Honest failure to recall unavailable information and clarification requests are acceptable; repeated failures affecting core use should still be reported. Record environment blockers separately from defects.

**Known limitations requiring focused QA:** extraction carries a bounded overlap rather than proving an arbitrarily long fact spanning more than a provider window; semantic classification and correction recognition are model-dependent despite exact-evidence and conservative checks. Multi-person association validation uses English capitalization and pronoun heuristics and may omit valid facts or miss ambiguity in other languages and formulations. Clarification is an instruction to the answer model, not a deterministic guarantee. Arbitrarily long summaries may not fit a recompression request. The current QA environment cannot perform browser or live-provider checks. A mock passing does not establish real-provider semantic accuracy. Treat any unsupported confirmed assignment, silent assumption promotion, fact loss, or original-history loss as P0.
